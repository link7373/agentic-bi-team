# Connections

> Created by Colin Beck — https://www.linkedin.com/in/beckcolin/

> How a generated workbook reaches data. Two paths, with very different levels of
> assurance - say which one you used.

## Assurance, stated up front

| Path | Schema-valid | Opened in Tableau | Verified against a live source |
|---|---|---|---|
| CSV (`textscan`) | yes | yes | yes - the demo dashboard |
| Live SQL | yes | **not by this project** | **no** |

The CSV path is the one this module can prove end to end. The SQL path emits
structurally correct XML and is the right shape, but no workbook built with it
has been opened against a real warehouse here. Treat your first one as unproven,
open it in Desktop before anyone else sees it, and report back what needed
changing.

## CSV extract - the default

```python
csv_connection("/abs/path/dashboards/exec/data/exec_kpis.csv", name="exec_kpis")
```

Emits Tableau's native `textscan` connection. Needs **no database driver** and
travels with the repo. Opens directly in Tableau **Desktop**.

For Tableau **Public**, pass `extract=True`. Public is extract-only - it cannot
open a live connection, and unlike the UI (which silently extracts a CSV for you
on connect) a generated workbook must declare the extract itself. See
`gotchas.md`.

The pattern is: mart -> CSV -> workbook, all regenerated by the dashboard's
`build.py`. See `.claude/skills/tableau/examples/demo-exec-overview/build.py`.

**When this is right:** the dashboard reads a summary table that fits comfortably
in a file, the refresh cadence is daily or slower, and you want anyone to be able
to open it without credentials. That covers most exec scorecards.

**When it is wrong:** row counts in the millions, sub-daily freshness, or data
that must not sit on disk as plaintext. `CLAUDE.md` §9 applies to a CSV extract
exactly as it does to any other export - if the mart has PII, the extract has PII.
Aggregate before exporting, don't export and then hide columns in the workbook.

Path handling and the absolute-vs-relative tradeoff are in `gotchas.md`.

## Live SQL

```python
sql_connection("postgres",
               server="warehouse.internal", database="analytics",
               sql="SELECT * FROM marts.exec_kpis",
               username="readonly_bi", port="5432")
```

Supported `kind` values: `postgres`, `bigquery`, `snowflake`, `redshift`,
`sqlserver`, `mysql`. Anything else raises `SpecError`.

Emits a federated connection wrapping a named connection of that class, with the
SQL as a custom-SQL relation.

### Credentials are never written to the workbook

`sql_connection()` takes a `username` and no password, and none is written into
the file. Tableau prompts on open, or uses a saved credential. **Never put a
password in a spec, a build script, or a `.twb`** - it would be committed to git
in plaintext. If a build needs a secret, read it from the environment at build
time and keep it out of the generated artifact.

### Per-warehouse notes

- **BigQuery** - `database` is the project; set `schema` to the dataset. Auth is
  OAuth or a service account configured in Tableau, not in the workbook.
- **Snowflake** - set `warehouse` as well as `database` and `schema`. A workbook
  pointed at an oversized warehouse is a recurring cost surprise.
- **Postgres / Redshift / SQL Server / MySQL** - `server` + `port` + `database`,
  with `schema` where the driver expects it.

Each needs its driver installed on every machine that opens the workbook. That is
the practical reason the CSV path is the default: it has no such requirement.

### Extracts over live connections

`standards/dashboard-standards.md` is explicit - extracts for anything a human
waits on. Every filter click on a live connection is a query and a cost. A live
connection earns its place only when sub-hourly freshness genuinely changes a
decision.

This module **does** generate `.hyper` extracts - `scripts/hyper_extract.py`,
`write_hyper()` and `package_twbx()`, gated behind `tableauhyperapi` which is
imported lazily so the CSV and SQL paths stay dependency-free. That covers the
CSV path end to end.

Extracting a **live SQL** source is not automated: the query would have to run
at build time with warehouse credentials, which is a deliberate non-goal here.
`validate_twb.py` raises `DSN001` on a live connection with no extract rather
than let it pass silently. Build the workbook, create the extract in Tableau,
and record the refresh schedule in `dashboards/README.md` - an extract nobody
refreshes is a dashboard that is quietly wrong.

## Custom SQL is a last resort, not the data layer

`sql_connection` takes SQL because it has to, not because putting transformation
logic there is a good idea. A `SELECT *` from a mart is the right use. A
200-line query with business logic in it is a mart that hasn't been built yet -
it is invisible to the catalog, untestable, and unreusable by the next workbook.
Route it to `/build-pipeline` and `analytics-engineer`.
